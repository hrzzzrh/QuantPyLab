# Tracking Calendar Triage Workflow

本 workflow 用于批量巡检 `investigation/equities/note.md` 中「跟踪审计日历」的已到期触发项，判断事件是否已经发生，以及是否需要转入单公司全量跟踪更新。

它只负责**日历巡检、事件核验、分流决策和必要的日历顺延**；不直接执行单公司的完整研报更新。若巡检判定某公司需要完整跟踪更新，应将该公司交给 `docs/workflows/intelligence-sync.md` 执行。

## 入口判断

当用户提出以下任务时，使用本 workflow：

- 检查 `note.md` 中「下次触发日」已过的条目。
- 检查某个边界之前的触发事件是否已经发生。
- 批量判断哪些公司需要进入完整跟踪更新。
- 将已发生但无需更新研报的触发事件顺延到下一个事件。

## 必读材料

1. `investigation/equities/note.md`
2. 巡检范围内每家公司对应的 `investigation/equities/<公司名>/跟踪手册.md`
3. 若某条触发事件涉及公告、财报、监管政策或行业数据，读取或检索相应的权威来源。

## 范围识别

1. 读取 `investigation/equities/note.md` 的「跟踪审计日历」表格。
2. 默认只检查「下次触发日」非 `—` 且已到期或已进入窗口期的条目；`—` 行不纳入巡检，除非用户明确要求。
3. 若用户给出边界（如“金诚信 07-月底及之前”），按表格中有触发日条目的排序截取到该行；不得跨过用户指定边界扩大范围。

## 逐项核验

1. 先阅读目标公司的跟踪手册，确认该触发事件在手册中的原始语境、重要性和后续事件序列。
2. 针对每个触发事件构造搜索词，至少覆盖：
   - `<公司名> <股票代码> <触发事件关键词> 2026`
   - `<公司简称> 公告 <触发事件关键词> <月份>`
3. 涉及政策、行业会议、海外监管或宏观变量时，补充监管机构、行业口径或英文关键词。
4. 优先使用公司公告、交易所、巨潮资讯、东方财富公告页、监管机构、权威行业数据发布方；新闻稿和媒体报道只能作为辅助证据。

## 状态分类

对每家公司给出且只给出以下四类状态之一：

1. **已发生且构成重大增量**：如新财报、业绩预告、重大订单、重大监管结果、足以改变核心变量的政策或价格冲击。
2. **已发生但不构成重大增量**：如例行分红除权、金额较小或已被上次审计覆盖的公告、只有日历窗口推进但无公司层面新事实。
3. **部分发生/窗口进行中**：政策进入审查、会议召开但结论未发布、公司只披露意向而非正式结果。
4. **未发生/无法核验**：未找到可靠公告或权威数据。

## 动作判定

1. **已发生且构成重大增量**：
   - 标记为「需要完整跟踪更新」。
   - 不在本 workflow 中直接改研报。
   - 若用户只要求盘点，输出待更新清单；若用户要求继续更新，再按 `docs/workflows/intelligence-sync.md` 对对应公司逐个执行。

2. **已发生但不构成重大增量**：
   - 不修改研报。
   - 在 `note.md` 中将该公司「下次触发日/触发事件」顺延为跟踪手册中的下一个尚未触发事件。
   - 保持「最后审计日」不变，因为没有进行完整跟踪审计。

3. **部分发生/窗口进行中**：
   - 通常保留当前触发项。
   - 如已有更精确的下一时点，可在事件描述中补充等待条件。

4. **未发生/无法核验**：
   - 保留当前触发项。
   - 在回复中说明未找到可靠证据。

后续事件必须来自该公司跟踪手册；若手册没有可用后续事件，再按 `note.md` 原维护规则留空为 `—`。

## note.md 维护

若修改 `investigation/equities/note.md`：

1. 只做与巡检结论相关的手术式更新。
2. 不推进「最后审计日」，除非已经另行完成单公司的完整跟踪审计。
3. 保持「跟踪审计日历」排序：有触发日的按日期升序在前，无触发日的按最后审计日升序（最陈旧在前）。
4. 临时脚本必须放在 `workspace/` 下运行并在任务结束前删除。
5. 收尾执行 `git diff --check`。

## 输出格式

巡检结果按公司逐行输出：

| 公司 | 原触发事件 | 事件是否发生 | 是否需要完整跟踪更新 | 简要说明 |
|:---|:---|:---:|:---:|:---|

如更新了 `note.md`，在回复中列出被顺延的公司及新的触发日/触发事件。
