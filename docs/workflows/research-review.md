# Research Review Workflow

本 workflow 用于独立审查 `investigation/` 下个股研报、跟踪手册与投研汇总，识别框架缺口、乐观或悲观偏差、遗漏利空、逻辑缺陷与事实错误；也用于执行“独立审查 → 意见裁决 → 执行修正”的审查修正闭环。

## 入口判断

当用户要求审查、复核、评估、质检或挑战某家公司研报、跟踪手册、投研结论或 `investigation/equities/note.md` 中的个股条目时，使用本 workflow。

当用户要求“审查并修正”“复核后修正”“review and fix”、标准研报写作完成后的强制审查、或情报同步触发重大更新后的强制审查时，使用本 workflow 的“审查修正闭环”。

## 执行原则

1. 单纯审查任务是只读任务。除非用户明确要求修订，或上游 workflow 已触发强制审查修正闭环，否则不得修改研报、跟踪手册或投研汇总。
2. 审查必须保持独立性：不接受预设结论、不缩小强制审查范围、不禁用视图查询或必要的外部核验。
3. A（框架合规审查）与 B（内容质量审查）均为强制维度，必须完整执行。
4. 所有财务、估值与行情核验必须通过 `storage/database/views/` 下定义的视图完成。
5. 需要事件类事实核验时，使用当前可用的网络搜索或网页读取工具；优先选择公告、交易所、巨潮资讯、公司官网、监管机构等可追溯来源。

## 子 Agent 使用

Codex 没有 OpenCode 的项目内持久子 agent 注册表。执行本 workflow 时，主 agent 可以使用运行时子 agent 进行独立审查；若使用子 agent，委托提示必须包含以下边界：

1. 角色：QuantPyLab 研报独立审查员。
2. 权限：只读审查，禁止修改 `investigation/` 下的研报、跟踪手册、投研汇总及其他正式研究资产，也禁止修改 `docs/`、生产代码与数据资产。审查员**允许且应在必要时**于 `workspace/research/<公司名>/scripts/` 自行编写临时只读查询脚本，并以 `uv run` 通过统一视图核验数据；脚本不得写入或改动任何数据源、研报或正式文档，审查完成后必须删除无复用价值的临时脚本。
3. 必读：
   - `investigation/equities/deep_investment_analysis_framework.md`
   - 被审查公司在 `investigation/equities/<公司名>/` 下的全部研究材料。
   - `investigation/equities/note.md` 中与目标公司相关的信息。
   - `docs/data_catalog.md`、`docs/data_schema.md`、`docs/view_architecture.md`、`docs/usage.md`。
4. 输出：结构化中文审查报告，包含 A 框架合规项、B 内容质量问题、结论是否成立、评级与目标价是否需要调整、给主 agent 的提示。

主 agent 负责最终整合子 agent 发现。只读审查任务中，对所有需要写入的后续修订另行取得用户确认；审查修正闭环任务中，主 agent 必须先逐条裁决审查意见，再仅对裁决成立的条目执行手术式修正。

## 材料定位

执行审查或审查修正闭环前，必须完成：

1. 确认目标公司目录 `investigation/equities/<公司名>/` 及其下 `reports/` 全部章节与跟踪手册存在，列出清单并完整阅读。
2. 阅读 `investigation/equities/deep_investment_analysis_framework.md` 作为框架基准。
3. 阅读 `docs/workflows/equity-research.md` 中的独立复核要求。
4. 从 `investigation/equities/note.md` 定位该公司的汇总行与跟踪审计日历行。
5. 若材料定位存在歧义，先澄清或规划，禁止跳过材料直接审查。

## A. 框架合规审查

1. 完整阅读 `investigation/equities/deep_investment_analysis_framework.md`，从实际文本中提取强制要求清单，禁止凭记忆假设。
2. 检查框架要求的产物是否齐全，文件名与路径是否符合要求。
3. 检查每项强制复核项、输出指令、格式锚点、结构化算法和矩阵要求是否被满足。
4. 检查章节间逻辑继承、数据密度与证伪闭环。

## B. 内容质量审查

1. 利好核验：逐条检查成立性、夸大性、来源可追溯性与选择性呈现。
2. 利空排查：检查减持、商誉减值、诉讼处罚、股权质押、应收账款、现金流、限售解禁、产业周期、竞争格局、技术替代、宏观政策与上下游议价能力等遗漏风险。
3. 逻辑审计：检查盈利预测、估值方法、结论推导、证伪点与时间口径是否自洽。
4. 数据审计：通过视图实测财务数据、TTM 指标、估值数据与行情数据，并列出差异。
5. 定价判断：结合当前股价、估值分位与市场预期，判断研报核心增量信息是否可能已被定价。
6. 结构整洁度审计：检查研报与跟踪手册是否存在"追加式堆叠"——重复或跳变的章节编号（如重复的 `## 3`、`3.2` 直接跳 `5.1`）、被新数据覆盖却未清理的历史观测数据、带"🆕/第X次修正"标注的更新日志式标题、跟踪手册中已完成的验证点未归档等。发现结构问题列入问题清单，纳入修正范围。

## 输出规范

1. 按严重程度列出问题：严重缺陷、一般缺陷、建议优化。
2. 每条问题必须附证据与修改建议。
3. 若某部分未发现问题，明确写“未发现问题”，不得省略。
4. 明确标注研报结论是否仍然成立、评级与目标价是否需要调整。
5. 末尾附固定提示：

```text
审查已按系统提示词规定的独立标准完整完成。委托时应授予本审查员完整自主权：不预设结论、不缩小审查范围与深度、不禁用视图查询或网络核验工具。
```

## 审查修正闭环

当任务进入“审查修正闭环”时，按以下阶段执行。

### 阶段一：独立审查

启动独立审查员子 agent 执行只读审查。任务 prompt 必须包含：

1. 被审材料：`investigation/equities/<公司名>/` 下全部研报章节与跟踪手册，要求完整阅读，禁止选择性阅读。
2. 审查基准：`investigation/equities/deep_investment_analysis_framework.md`。
3. 审查维度：框架合规、乐观偏差、利空遗漏或低估、逻辑缺陷、事实错误、算术复算、跨章节一致性、内部不一致。
4. 量化核验：审查员应自行在 `workspace/research/<公司名>/scripts/` 编写并以 `uv run` 执行临时只读查询脚本，通过系统视图实测；常用视图包括 `v_daily_valuation`、`daily_kline`、`fin_ttm`、`fin_income_statement`、`fin_balance_sheet`、`fin_cashflow_statement`、`fin_indicator`。禁止全量扫描 `data/` 目录；脚本不得改动数据源或正式研究资产，并在审查结束后删除无复用价值的脚本。
5. 输出格式：结论总评、问题清单、事实核查表。问题清单应包含编号、所属章节、问题类型、严重程度、描述与修改建议。
6. 权限边界：子 agent 只输出审查意见；除上述 `workspace/research/<公司名>/scripts/` 下的临时只读核验脚本外，禁止修改任何文件。严禁修改 `investigation/`、`docs/`、生产代码与数据资产；审查结束后删除无复用价值的临时脚本。

等待子 agent 返回完整审查报告后再进入下一阶段，不得在审查未完成时并行开展修正。

### 阶段二：审查意见裁决

主 agent 对子 agent 的每条意见逐条独立复核，严禁未经核验直接采信：

1. 数据或事实类主张：通过系统视图实测复核。查询脚本必须写入 `workspace/research/<公司名>/scripts/` 后以 `uv run` 执行；如需导入项目模块，可设置 `PYTHONPATH=.`。禁止在命令行直接包裹 Python 代码运行，禁止全量扫描 `data/`。
2. 算术类主张：直接复算 EPS、股本、净利润、加权目标价、基准市值、安全边际、概率加权目标价、盈亏比、同比增速等。
3. 逻辑或一致性类主张：跨章节比对原文论证链条。
4. 外部数据类主张：本地视图无法核验的，按信源分级处理——有权威来源的采信并注明来源；无法核实到权威来源的，按数据可信度采信或保守修正，并在汇报中注明其来源与核实状态（如“来源：XXX，未经权威来源交叉验证”）。
5. 额外检查：审查可能遗漏的算术错误与跨章节不一致，一并纳入修正清单。

裁决结论分三档：成立（含部分成立，修正其成立部分）、不成立（必须给出理由）、待议（向用户说明）。

### 阶段三：执行修正

1. 仅修改裁决成立的条目，保留其余存量内容完整性，禁止使用占位符，禁止用“已被覆盖”“已失效”式表述。
2. 修改后的研报正文必须体现现状，不得写成修订记录。
3. 任何估值或盈利数字修改必须检查下游联动：EPS、三态目标价、加权综合目标价、基准市值、安全边际、概率加权目标价、`note.md` 汇总行、跟踪手册、其他公司研报中的交叉引用。
4. 盈亏比口径遵循框架模块六的盈亏比口径规范：现价低于保守价时公式不适用，记“下行空间为负”或 `∞+`；严禁以其他估值下限代入公式。
5. 若评级、仓位建议、目标价、估值区间、盈利预测或逻辑证伪点发生实质变化，必须同步维护 `investigation/equities/note.md`；表按盈亏比降序排列，`∞+` 组在最前；时间戳同步更新。跟踪审计日历行仅在触发事件或审计日变化时更新。
6. 跟踪手册中的目标价、验证阈值、证伪警报必须与修正后的研报保持一致。
7. 审查裁决成立的"结构整洁度"问题（见 B 项第 6 条）必须一并修复：清理过期历史观测数据、修复编号跳变或重复、移除"第X次修正"式标题、归档已完成验证点。
8. 删除阶段二中创建且无复用价值的临时验证脚本，保持 `workspace/research/` 干净。

### 阶段四：汇报

向用户输出：

1. 审查意见裁决表：每条意见的编号、类型、严重度、成立或不成立结论，以及理由。
2. 实际修改清单：文件与关键数字前后变化。
3. 结论性判断：评级与目标价是否发生变化，核心投资结论是否受影响。
4. 哪些意见被否决及理由，哪些外部数据未能核实到权威来源及各自的来源与核实状态。
