# 交易容量与流动性诊断设计

**设计日期**：2026-08-21
**设计状态**：已确认执行（依据用户授权持续自主开发）
**实现范围**：研究专用诊断，不改变正式策略、因子权重或成交规则

## 1. 背景与目标

前面的因子诊断和多因子边际贡献验证已经回答了信号是否存在、因子是否提供增量信息，但还没有回答目标组合是否能够以当前回测资金规模交易。换手和手续费只能描述回测引擎按照给定初始资金产生的结果，不能单独说明订单相对于标的日常成交额是否过大。

本功能增加一个独立的交易容量诊断，使用正式 `multi-factor-quality-value-momentum` 策略的同一目标和同一 `DailyBacktestEngine`，输出：

- 信号日候选池的滚动成交额覆盖率和市值覆盖率；
- 20 个交易日历史平均成交额、成交额/市值的分布和分组选择偏差；
- 每笔调仓订单相对于信号日前可知流动性的参与率；
- 在 5%、10%、20% 订单参与率上限下的简化资金容量估算；
- 退市清算、无法匹配信号日流动性和跳过调仓等非容量原因的单独计数。

诊断结果用于发现回测组合的可交易性风险，不自动把流动性条件接入正式策略，也不以容量估算替代真实冲击成本模型。

## 2. 点时数据协议

### 2.1 输入

- 行情：`daily_kline.amount`，单位为元；
- 估值：`share_capital`、`fin_ttm` 和 `fin_balance_sheet`，由 `BacktestDataAccess` 统一构造点时 `market_cap`；
- 因子和目标：沿用正式多因子策略的因子版本、上市天数、月末信号日、缩尾、排名、持仓数量和目标权重；
- 成交：沿用 `DailyBacktestEngine` 的下一交易日开盘、后复权价格、手续费、滑点和退市清算。

### 2.2 流动性快照

对每个股票按交易日排序，计算（默认窗口为 20 个交易日，实际窗口由命令参数记录）：

```text
avg_amount(date) = amount(date) 及之前 N 个交易日成交额的算术平均值
amount_to_market_cap(date) = avg_amount(date) / market_cap(date)
```

窗口包含信号日收盘成交额，因为月末信号是在收盘后产生；不包含下一交易日的成交额，也不使用未来的成交量或成交额。窗口不足 20 个有效交易日时返回缺失。非有限成交额和非有限市值不进入有效覆盖统计；零成交额会保留在窗口中，但滚动均值为零时不能作为可交易流动性快照。

### 2.3 订单参与率和容量

回测交易记录中的 `notional` 是按配置初始资金产生的订单金额。对有 `signal_date` 的 BUY/SELL 调仓订单：

```text
order_participation = abs(notional) / avg_amount(signal_date)
capacity_capital(limit) = initial_capital * limit / order_participation
```

默认参与率上限为 5%、10% 和 20%，可通过命令行参数覆盖。容量按单笔订单估算，报告同时给出各上限下的最小值、P10、中位数和 P90。它没有模拟价格冲击、盘口深度、涨跌停、整手、成交时段或多订单之间的竞争，因此必须明确标为“参与率近似容量”，不能解释成可保证成交的实盘容量。

## 3. 报告与接口

新增研究命令：

```bash
uv run main.py diagnose-factor-liquidity-capacity \
  --backtest-config config/backtest/multi_factor_quality_value_momentum.toml \
  --evaluation-start-date 2022-07-01 \
  --evaluation-end-date 2024-06-30 \
  --output workspace/factor_liquidity_capacity/...
```

第一期只支持正式多因子策略，以保证诊断目标与正式策略完全一致。评估日期必须成对指定；显式区间才标为锁定评估区间。

报告目录固定包含：

- `summary.md`：数据口径、未来函数审计、信号日覆盖、订单参与率、容量分位数、限制和结论；
- `parameters.json`：解析后的回测配置、评估区间、窗口、参与率上限和版本信息；
- `liquidity_signal_summary.csv`：逐信号日候选数、选中数、成交额/市值有效覆盖和分布统计；
- `liquidity_buckets.csv`：逐信号日按平均成交额分组的候选与选中占比；
- `liquidity_trades.csv`：逐笔交易与信号日流动性快照、参与率和容量估算；无效名义金额订单单独标记；
- `liquidity_capacity_summary.csv`：各参与率上限的订单数量、缺失数量和容量分位数。
- `liquidity_targets.csv`：正式策略实际送入回测引擎的信号日目标权重；
- `liquidity_backtest_summary.csv`、`liquidity_daily_nav.csv`：正式策略回测基线的汇总和逐日净值。

本次实现同时补强了容量诊断依赖的点时可复现性：TTM、资产负债表和指标的原始历史行先通过统一视图按请求股票范围读取，再在 Python 中按股票、生效日、报告期、文件名和数值字段确定性去重，最后用 `searchsorted` 回溯到不晚于信号日的最近生效行；不依赖 DuckDB ASOF 或大型区间连接的执行计划。行情先通过 `daily_kline_calendar` 和 `daily_kline_raw` 读取；只有存在重复 `(symbol, date)` 时才加载完整 tie-break 字段并按既有 `daily_kline` 规则确定性去重。容量报告只有在同一输入的独立进程重复加载结果一致时才作为最终结果。

### 3.1 内存边界

诊断会先计算一次完整策略候选，再从同一候选表生成目标，避免重复执行因子计算；流动性快照只保留候选信号日，回测阶段只传入 `date`、`symbol`、`open`、`open_hfq` 和 `close_hfq` 五个必要字段。回测引擎按交易日保存紧凑的数值行情表，不为每个行情行创建 Python 嵌套字典。财务历史先物化、行情后读取，避免在大型行情表驻留期间再次触发财务 Parquet 扫描；DuckDB 结果在进入 Pandas 后立即建立独立内存所有权，诊断在信号数据物化后关闭 DuckDB 查询缓存。

正式报告必须串行运行；重复性验证不得并发保留两份全量信号表。回测数据访问将 DuckDB 查询限制为 2GB 和 2 个工作线程；统一视图只读取原子晋级后的 `data.parquet`，排除同步临时/备份文件；调试脚本不得把完整行情 DataFrame 长期写入多个列表或报告对象。锁定区间正式诊断双跑的峰值记录约为 3.71 GiB 和 3.16 GiB，结果文件除生成时间外一致。

## 4. 不在本次范围内

- 不修改正式多因子策略的目标生成、因子权重和 `DailyBacktestEngine` 成交规则；
- 不把执行日完整成交额用于容量分母；
- 不把成交额/市值直接注册为 alpha 因子；它先作为可交易性诊断和风险过滤候选；
- 不承诺真实市场冲击成本，不接入盘口、分钟线或外部成交概率模型；
- 不因流动性缺失而偷偷删除正式目标，缺失只进入覆盖和容量审计。

## 5. 验收标准

1. 数据访问层能显式请求 `amount` 和 `market_cap`，且不破坏既有因子字段选择测试。
2. 单元测试验证 20 日窗口不使用下一交易日数据、窗口不足和无效输入的处理、参与率及容量公式、目标/交易匹配和报告文件契约。
3. 在锁定的 `2022-07-01..2024-06-30` 区间运行正式多因子组合，目标、成交和净值沿用同一引擎并完成未来函数审计。
4. 真实报告明确区分有效订单、缺少信号日流动性、跳过调仓和退市清算，不伪造容量数值。
5. 通过 Ruff、全量测试和 Review Gate 后提交代码与文档；真实生成的报告保留在 `workspace/`，不纳入代码提交。
6. 在锁定区间执行正式诊断时，因子输入、候选、目标和回测行情不得重复驻留不必要的宽表；重复运行的结果必须一致。
